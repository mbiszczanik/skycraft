# Lab Portal Pass

Walk a SkyCraft module's lab guides in the Azure Portal as a learner would, find where guide and Portal disagree, and hand the maintainer one standard report plus the decisions only they can make. The repository receives issues and comments only; this skill never edits the repo, commits or opens PRs unless the user asks.

## Workflow

0. **Check capabilities before live work.** Discover the available browser tools for navigation,
   page inspection, clicking, typing, screenshots saved locally, and dialog handling. Read
   `references/portal-automation.md`. Paths in this skill are relative to its folder
   (`.agents/skills/lab-portal-pass/` in the repository). If required browser capabilities are unavailable, the pass
   shall stop before touching a live environment and report the missing capabilities.
1. **Read first, click later.** Record the guide commit: `git -C <repo> fetch -q; git rev-parse --short origin/main`. Export the module's `lab-guide-*.md`, `lab-checklist-*.md` and `scripts/` from that commit (`git show origin/main:<path>`) into the scratchpad and read them. Read the tracking issue (#300 or its successor), #329's table, and every open issue that names the module, so known defects are recognised and not refiled. Then list the **steps only the user can do** (see `references/safety-and-accounts.md`, "Steps the agent does not do") and tell the user before the walk: prepare the files and exact commands for them, and batch them into one short session with the user per module instead of interrupting the walk.
2. **Pre-flight (read-only).** Run `bash scripts/preflight.sh <subscription-id>` (a permission prompt may appear) and inventory Entra objects in the Portal. Report what already exists. Ask how to proceed when lab objects, policies or a live estate are present, and ask the user to confirm nothing else runs in the subscription. Accounts, tenants and safety rules: read `references/safety-and-accounts.md` before step 3.
3. **Walk each lab in order.** Do exactly what each step says from where the previous step left the screen. Use only what the guide gives. When a label, menu path or default differs, note the exact Portal text, take the obvious learner move and record it. On every wizard and settings page, look for **defaults that cost money, delete data or open access** and record each one even when the guide is silent (`references/classification-and-evidence.md`, "Risky defaults"). Check every Expected Result. Screenshot each discrepancy, save it to disk, then copy it to `<scratchpad>/shots/<step>[a-z]-<slug>.jpg`. Classify each step (definitions and evidence rules: `references/classification-and-evidence.md`). Record each step into `pass.json` as you go (shape: `templates/pass.example.json`). Chrome and Portal handling: `references/portal-automation.md`.
4. **Validate each lab.** Run its `scripts/Test-Lab.ps1` from the exported commit, read-only, and save the full output to `<scratchpad>/testlab-<lab>.txt` with its exit code; in `pass.json` put that path in `testlab.log` and only an excerpt in `testlab.output`. Never type pass/fail counts by hand: `render_report.py` reads them from the log, and refuses counts the log does not print. Label failures that are known issues as such. Entra labs need an interactive Graph sign-in: give the user a command for their actual shell; ARM labs run in-session (see the safety reference).
4a. **Check parity before the next lab.** Each lab must reach the same end state in the Portal, with PowerShell / CLI and with its Bicep (#362). Right after Test-Lab, run the lab's `Deploy-Bicep.ps1 -WhatIf` against the Portal-built state through `scripts/run-azps.ps1` (read-only; the wrapper refuses a real deploy), classify every reported change as difference or noise, and mark which change-steps have no Bicep or no scripted counterpart. Procedure, recording shape and known noise: `references/parity.md`.
5. **Search the class before filing.** For each WRONG / BLOCKED / script defect, search all 17 labs for the same pattern (delegate the sweep to one read-only search agent, if available, with the questions listed in `references/classification-and-evidence.md`). File one issue per class; add evidence to existing issues instead of refiling; put guide-wording drift into the module's #329 guide-PR issue (`[Bug]: Lab X.Y: guide steps no longer match the Azure Portal`).
6. **Report.** Before writing anything public, read `references/redaction.md`. Fill `pass.json` (findings, issues, live state, decisions - start from `templates/decisions-bank.json`, keep the questions that apply, add lab-specific ones). Run `python scripts/render_report.py <pass.json> <out-dir>`: it first validates `pass.json` (unknown keys, results, counts; exit 3 = nothing written), then writes `comment-<lab>.md` per lab, `report.html` (one per module, in the user's language) and `panel-report.json`, and scans the comments for identifying data with the publication guard, if installed (`PUBLIC_CONTENT_GUARD`, see `references/redaction.md`). Post each comment to the tracking issue (lab 1.2-type exceptions go where the user says) and give the user `report.html`; publish it as a private page only when the user asks for a link. Optional: if the agents-config panel is available (`AGENT_CONFIG_REPO`), also write the report there: `python "$AGENT_CONFIG_REPO/tools/panel_store.py" write report <project> <out-dir>/panel-report.json --page <out-dir>/report.html`, where `<project>` is the lab repository's folder name. Exit 3 lists what fails validation and leaves the panel unchanged: report the panel as not updated and fix `pass.json`, not the tool. Give the panel address (`http://127.0.0.1:8765/`; start `python "$AGENT_CONFIG_REPO/tools/panel_server.py"` in the background when it does not answer).
7. **Act on the decisions.** Read the maintainer's answers (the text copied from `report.html`'s **Copy answers**, or, when the panel is used, `python "$AGENT_CONFIG_REPO/tools/panel_store.py" answers <project>`, scope `report:<report id>`); never assume an answer. With the panel, act only on answers with `"current": true`; an answer to a decision a later pass changed or dropped is history, so ask again. Execute only what they chose, re-checking the subscription id and the object's state immediately before every delete. Record outcomes and chosen fix approaches as comments on the issues. **When** a maintainer step that something waits for is done, **the agent shall** update every place that says it is pending in the same session: the #329 row, the module report (`pass.json`, re-render, write to the panel again if used) and the issue comment.
8. **Verify each fix live before asking to merge it.** When a fix PR for a finding is pushed, re-run on its branch, in the test tenant, the steps that failed and the affected labs' `Test-Lab.ps1`, with `$LASTEXITCODE` reset before each in-session call. Declare `Live-verified: <what ran, date, exit codes>` in the PR and post the redacted run to the tracking issue. Defer only a check the test environment cannot run (brand-new subscription, unconsented account, Cloud Shell) and give the blocker line ADR-0006 asks for. Close the issue from the PR (`Closes #N`) only when every live item of it ran on the branch; otherwise link `Refs #N` and list what is still owed. The check is not repeated on `main` after the merge (ADR-0006).

## Gotchas

- Sign-in, MFA and passwords are the user's. Never type a password into the Portal; leave "Auto-generate password" on and record it as a deviation.
- `az` CLI's default context drifts between tenants: pass `--subscription` on every call and set `MSYS_NO_PATHCONV=1` in Git Bash, or `/subscriptions/...` scopes silently become Windows paths.
- In today's Portal, **Assignment name** in Assign policy sets only the display name (#330). Remove Portal-made assignments by their generated names, after removing locks.
- A Portal create can fail with the reason only under the notification bell; read it there and in `az monitor activity-log list --offset 30m` before calling a step OK or WRONG.
- Never `az account set`: it changes the user's default context for every other session. Pass `--subscription` instead.
- The agent's permission mode may refuse some steps (rotating keys, granting yourself a role, generating SAS). Do not work around a refusal (no `--auth-mode key`, no other identity): the step goes to the user's list.
- Do not assume chat supports a `!` shell escape or that it runs bash. Give a terminal command using
  the user's shell, including its exit-code syntax.
- Check whether the publication guard is installed rather than assuming it. When it refuses, redact and retry, never route around it. A missing guard
  is not evidence that content is safe: review and redact before any authorised publication.
- Never `git stash` in the repository: the stash is shared by every worktree and every session. To prove a test fails without a fix, edit a copy of the file and restore it from the copy.
- **When** a test is added for a fix, **the agent shall** run it once against the code without the fix and record that it failed. A stubbed rule-set test passed both ways on 2026-10-25 until the stub returned the cmdlet's real shape.
- **Before** a fix PR is declared ready, **its branch shall** contain the current main and the full CI test set shall have run at that head. A CONFLICTING PR runs no CI, and main's new rules (#397, #375) failed two Module 4 branches only after the merge.
- **The agent shall** run a PR's final live check after the PR's last guide or script edit; a later edit makes every evidence line need "the later commits change only ...".
- **When** the pass posts a finding about a guide step, or runs a deploy or teardown script from the local checkout, **the agent shall** first `git fetch`, compare that step or script with `origin/main`, and fast-forward the local `main` checkout.
  A finding on Step 5.2.4 was already fixed by #469, and a teardown from a stale local `main` left Lab 5.1's heartbeat alert behind (2026-11-02).
- **Before** the agent orders a live or Portal pass, **it shall** map each owed item to recorded evidence (PR `Live-verified:` lines, issue comments, dated tests) and brief only the gaps.
- **When** a PR lists unchecked items, **the list shall** name only items its diff changes.
  10 issues were triaged as owing live checks that earlier passes already covered, and #474 listed unchecked items outside its diff (2026-11-02).

## Resources

- `references/safety-and-accounts.md` - accounts per lab type, tenant/subscription guards, approvals, live-estate rules, Test-Lab sign-in recipes. Read before clicking.
- `references/portal-automation.md` - browser automation and Portal quirks (stalled views, input timing, confirmation fields, screenshots).
- `references/classification-and-evidence.md` - OK/DRIFT/WRONG/BLOCKED, what counts as evidence, where each finding goes, the class-search questions.
- `references/parity.md` - the three-path parity check (what-if against the Portal state, classifying changes, coverage of Bicep and scripted paths).
- `references/redaction.md` - what may not appear in public text and the placeholders to use instead.
- `templates/pass.example.json` - the data shape (the Module 1 pass of 2026-10-14, redacted); copy and fill.
- `templates/decisions-bank.json` - standard decision questions to start the decisions list from.
- `templates/report.html` - the layout of the full report page; `render_report.py` fills it, do not edit per run.
- `scripts/preflight.sh` - read-only subscription inventory; run it with `bash`.
- `scripts/run-azps.ps1` - runs Test-Lab.ps1 or Deploy-Bicep.ps1 -WhatIf with a process-scoped Az context; exit 99 when the script crashed.
- `scripts/render_report.py` - renders the comments, the HTML report and the optional panel report from pass.json and scans for identifying data; run it.
