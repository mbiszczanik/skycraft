### Added

- `tests/Lab11-Graph-Auth.Tests.ps1`: pins the Lab 1.1 Microsoft Graph sign-in without a tenant, lifting `Get-LabGraphAuthPlan` out of the lab scripts with the PowerShell parser the same way `tests/Lab53-Cleanup-Logic.Tests.ps1` does (#76). The cases that matter are the ones no live run reaches on purpose: a fully configured service principal, one configured by halves, none at all, and none at all in a session that cannot prompt. It also asserts the three copies of the decision stay byte-identical - `docs/powershell-standards.md` §7.3 requires each lab folder to be self-contained, so the duplication is deliberate and the drift is what needs guarding - and, where `Microsoft.Graph.Authentication` is installed, that each mode's parameters bind to exactly one real `Connect-MgGraph` parameter set rather than to two or none.
- `tools/Invoke-DryRun.ps1`: a single offline pre-push gate that mirrors every CI check runnable without `az login` and without deployed resources (#64). It parses every `*.ps1`/`*.psm1`/`*.psd1` with the PowerShell parser, runs `Invoke-ScriptAnalyzer` against `PSScriptAnalyzerSettings.psd1` (gating on `Error` only, like CI, while listing warnings), and compiles every Bicep entry point and every `.bicepparam` with `az bicep build` / `az bicep build-params`. Every selected check runs to completion, so one run reports every problem rather than only the first, and the consolidated summary exits non-zero on failure. Missing tooling fails the affected check with an install hint instead of passing quietly, and checks left out with `-Check` are reported as `SKIP` so a partial run cannot be mistaken for a full one. Compilation goes through `--outfile` rather than the workflow's `--stdout`, because `az bicep build --stdout` dies with a `UnicodeEncodeError` on a non-UTF-8 Windows console as soon as a template pulls in an AVM module whose metadata contains a non-ANSI character.
- `docs/dry-run-harness.md`: how to run that gate, what each check mirrors, and the copy-paste `az deployment ... what-if` / `Test-Lab.ps1` / `Remove-LabResource.ps1` commands for each of the 17 labs - the live verification that needs `az login` plus existing resources and is therefore documented rather than executed. It also records which labs cannot be previewed with a raw `az deployment sub what-if` against their checked-in parameter file: all of Module 5, whose files carry placeholder resource IDs under the zero subscription GUID so `az bicep build-params` can validate them offline while the deploy scripts resolve the real IDs at run time, and Lab 3.2, whose SSH public key comes from an environment variable. Those go through `Deploy-Bicep.ps1 -WhatIf` instead.
- `tests/Lab21-Subnet-Link-Preflight.Tests.ps1`: pins the Lab 2.1 teardown preflight without an Azure call, lifting its decision helpers with the PowerShell parser the same way `tests/Lab53-Cleanup-Logic.Tests.ps1` does for Lab 5.3. The live subscription can only ever show the one orphaned link, so the shapes that matter - no links, several links across several subnets, a link whose target still exists, a target that could not be resolved - are pinned here instead. It also guards the return-shape trap the helper was written around: wrapping the result in a unary comma would make every inline `@(Get-SubnetServiceLink ...)` capture report a count of 1, empty results included.
- `tests/Lab53-Cleanup-Logic.Tests.ps1`: the repository's first behavioural test. Every other suite in `tests/` matches source text; this one lifts the decision helpers out of Lab 5.3 `Remove-LabResource.ps1` with the PowerShell parser (evaluating only the `FunctionDefinitionAst` nodes, so the script body never runs and no Azure call is made) and exercises them against synthetic input. It exists because the `NWTA-*` branch added in #106 could not be verified against live Azure: Traffic Analytics materializes its data collection rule and endpoint only after processing real flow data for a sustained period, and a purpose-built environment with a correct Traffic Analytics configuration, captured flow-log blobs and forced traffic did not produce them in ~86 minutes. Endpoint filtering, target de-duplication, the `Project = SkyCraft` ownership guard, the `NWTA-*` type/prefix filter, the rule-before-endpoint deletion order and the still-feeding guard are now pinned in 19 tests that run in seconds.
- `scripts/Invoke-ResourceAudit.ps1`: reports Azure resources tagged `Project=SkyCraft` that no lab source accounts for (#116). A `Standard_B2ls_v2` VM - `prod-skycraft-swc-traffic-vm` - ran and billed in `prod-skycraft-swc-rg` while nothing in this repository referred to it, and its NIC in `AuthSubnet` would have blocked the prod VNet teardown with the same `InUseSubnetCannotBeDeleted` symptom as the orphaned `serviceAssociationLink` in #110. The string `traffic-vm` appears in **no commit** in this repository's history, so the resource was never described here at all - it was created out of band while carrying the canonical tag set. The audit is deliberately **not** a literal name grep: roughly half of all resource names are composed at deploy time from an environment parameter and a suffix (`'${varNamePrefix}-kv'`, `"$Environment-skycraft-swc-vnet"`) and never appear in the sources as literals, so grepping for the literal name flags `prod-skycraft-swc-kv`, `-asp` and `-app01` - all legitimate, actively deployed resources - exactly as loudly as it flags the real orphan. Instead the audit rebuilds the set of names the repository can produce, keeping the literal ones and expanding the composed ones over the domains the templates constrain with `@allowed` - environments and locations both, since Lab 5.3 names the Network Watcher `'NetworkWatcher_${parLocation}'`. The discriminator is the suffix, which for a real lab resource is always one some template emits. It reports and exits **1** on drift, and deletes nothing, so a false positive cannot tear down live lab state.
- Scope is two things, not one: resources carrying the project tag anywhere in the subscription, and every resource inside a resource group the repository names, tagged or not. The tag query alone has a blind spot - anything created without tags is invisible to it, and an untagged VM in a lab resource group is #116's teardown-blocking case exactly. Found live: `NetworkWatcherRG` really does sit in this subscription carrying no tags at all, and the tag query never saw it.

### Fixed

- Lab 1.1's three scripts sign in to Microsoft Graph app-only when a service principal is configured, and no longer hang waiting on a prompt nobody can answer (#76). `Connect-MgGraph -Scopes ...` binds the **delegated** parameter set, so a run whose cached token needed a refresh the broker could not complete silently sat on an interactive prompt - the only unstable step in an otherwise green cycle, mitigated until now with a four-minute step timeout, which turns a hang into a killed phase rather than into a run that works. `Get-LabGraphAuthPlan` now makes the sign-in a decision that can be read and tested on its own: with `SKYCRAFT_GRAPH_TENANT_ID`, `SKYCRAFT_GRAPH_CLIENT_ID` and `SKYCRAFT_GRAPH_CERT_THUMBPRINT` (or `SKYCRAFT_GRAPH_CLIENT_SECRET`) set it returns the app-only parameter set, which never prompts; with none of them set it returns the interactive plan the lab has always used, and a learner sees no change. Set **by halves** it returns neither and the script stops naming the missing variable - falling back to a prompt there would reintroduce exactly the hang - and a caller that has declared itself unattended with `SKYCRAFT_UNATTENDED` fails in seconds instead of waiting out a step timeout. App-only never reuses a cached delegated context, because that context is what hangs on refresh. That environment variable is the *only* thing treated as 'nobody is watching': sniffing the console instead was tried, and `[Console]::IsInputRedirected` refuses a sign-in to a learner who is sitting right there the moment anything redirects a stream. Lab 1.1 is run by hand - it is not in `tools/lab-cycle-manifest.psd1` - so refusing a prompt someone could have answered is the failure that would actually happen, and the hang it would have caught is the one that would not. The variables are deliberately not the Azure SDK's `AZURE_CLIENT_ID` trio: those are usually already exported for the subscription identity, which in this project is a different account from the one that administers Entra ID, so consuming them would sign Graph in as the wrong principal, silently. The service principal is **optional** and no lab cycle needs one today; `TROUBLESHOOTING.md` carries the one-time setup for whoever automates 1.1 - the four Graph **application** permissions the lab actually needs (`Directory.ReadWrite.All` is not one of them), certificate over secret, SecretManagement rather than a file, and rotation.
- Lab 1.1's `New-LabUser.ps1` no longer installs the `Microsoft.Graph` meta-module behind the learner's back (#76). Its `#Requires -Modules` line already blocks the script when a submodule is missing, so the `Install-Module Microsoft.Graph -Force` block could only ever fire when the submodules *were* installed correctly - per `TROUBLESHOOTING.md`, which recommends exactly that - and it then installed some forty modules, for minutes, for nothing.
- Lab 1.1's three scripts declare the Graph submodules they actually use (#76). All three call `Get-MgDomain` from `Microsoft.Graph.Identity.DirectoryManagement` and `New-LabUser.ps1` calls `New-MgInvitation` from `Microsoft.Graph.Identity.SignIns`, neither of which was in any `#Requires` line: a host that installed only the three documented submodules resolved no `Get-MgDomain`, fell into the catch, and fell back to the literal `onmicrosoft.com` - not a verified domain in any tenant, so every user creation then failed on a UPN the script had made up. `TROUBLESHOOTING.md`'s install line names all five submodules now.
- Lab 5.2 `Deploy-Bicep.ps1` creates `SkyCraft-Daily-Prod` as an **Enhanced** backup policy and no longer reports a failed deployment as a success (#113). Azure defaults VM deployments to Trusted Launch, which a Standard policy cannot protect, so enabling VM backup failed with `UserErrorThisVMBackupIsSupportedUsingEnhancedPolicy` for every VM in the lab — and the script printed a `[WARNING]` and exited 0, so an orchestrated cycle recorded a lab whose central resource was never created. Failed policy creation and failed VM protection are now counted and exit 1. Enhanced keeps instant-restore snapshots for 7 days by default, so the script pulls that back to the 2 days the lab documents and `Test-Lab.ps1` asserts. The idempotency check no longer relies on `FriendlyName`, which Azure can return empty.
- Lab 2.1 `Remove-LabResource.ps1` reports orphaned `serviceAssociationLink`s before it deletes anything (#110). `AppServiceSubnet` on `prod-skycraft-swc-vnet` carries a link naming an App Service Plan deleted long ago, which makes the VNet delete fail with `InUseSubnetCannotBeDeleted`; since #96 and #104 that failure is visible and exits 1, but it was only diagnosed *after* the delete had been attempted. A preflight now lists the service association links on the subnets of every lab VNet and reports, per link, whether the resource it names still exists - an orphan is called out by name together with the ARM error it will cause. The preflight is diagnostic only: it never feeds `$script:cleanupFailures`, so a reported link cannot turn an otherwise clean teardown red and the exit code still reflects what the deletes actually did.
- Lab 3.4 `Remove-LabResource.ps1` comment-based help no longer claims the site's `networkConfig/virtualNetwork` route "answers 404 once detached" (#110). The code has always treated both 404 and 200-with-an-empty-`subnetResourceId` as detached; only the summary was wrong. A 404-only check is a known trap - it reads a perfectly detached site as still attached and burns the whole three-minute wait budget.
- Every automation script now sets `$Host.SetShouldExit(<code>)` immediately before a non-zero `exit`, so a failed run is visible to its caller (#104). PowerShell 7 discards `exit <code>` from a script run as `pwsh -File` when that script declares `#Requires -Modules` for a module it has to auto-import - which every `Az.*` script here does. The `exit` still ran, but the process reported **0**, so the lab cycle recorded a failed teardown as a clean one; Lab 2.1 cleanup printed `Cleanup finished with 1 failure(s)` and exited 0. The same script exits correctly when dot-called or run with `-Command`, which is why only the automated cycle was affected. Applied to 144 exit sites across 55 scripts and enforced by the new `tests/Exit-Code-Propagation.Tests.ps1`, which asserts the guard structurally and verifies that the idiom really carries the code through `pwsh -File`.
- Lab 5.2 `Remove-LabResource.ps1` no longer masks teardown failures (#105). Each of its delete steps reported a `[WARNING]` and the script always exited 0, so a run in which every step failed still printed `Cleanup Complete`. Failures are now reported as `[ERROR]`, counted, and the script exits 1 — while still continuing past a failure, so one stuck resource does not strand the rest. The Recovery Services Vault failure hint no longer claims the vault must be emptied through the portal first: it names the real modern cause, tooling older than Azure CLI 2.75.0+ / Az PowerShell 7.5.0+, which is also checked up front so a stale `Az.RecoveryServices` is diagnosed before the delete is attempted. Teardown additionally removes the orphaned `Microsoft.Compute/restorePointCollections` container Azure Backup leaves behind and the `AzureBackupRG_<location>_*` group holding it, once that group is empty.
- Lab 3.2 `Deploy-Bicep.ps1` takes a `-Force` switch and no longer confirms the deployment by reading stdin (#103). Run non-interactively, the old `Read-Host` prompt read EOF, printed `Deployment cancelled.` and exited **0**, so an orchestrating chain recorded the skipped VM deployment as a success and only failed two labs later. The confirmation is now a host prompt defaulting to No instead of a stdin read: `-Force` deploys without asking, and a declined confirmation - or a session with no console to prompt on - exits **2** having deployed nothing.
- Lab 5.3 `Remove-LabResource.ps1` now cleans up everything the deployment creates, not just the connection monitor and the flow log (#106). It also removes the `NetworkWatcherAgent` extension that `Deploy-Bicep.ps1` installs on both connection monitor endpoint VMs — resolved from the monitor's own endpoints before it is deleted, skipped for a missing VM, a missing extension, or an agent not tagged `Project = SkyCraft` — and the `NWTA-*` Traffic Analytics data collection rule and endpoint Azure creates next to the Log Analytics Workspace, once no flow log with Traffic Analytics is left to feed them.

The AVM module skips a sub-service whose parameter is empty, so a lab that does not own a sub-service passes `{}` and cannot regress an earlier lab; account-level properties are a full replace, so every lab restates the same baseline. Lab 4.4 is the only lab that has to restate another lab's blob configuration, because it creates `dev-assets`.

Lab 5.2 `Test-Lab.ps1` asserts `AlwaysON` accordingly, and the teardown path — deleting a vault that holds only soft-deleted items — requires Azure CLI 2.75.0+ or Az PowerShell 7.5.0+.

- Module 5 resource deltas from the AVM conversion: the Log Analytics workspace is created with `features.disableLocalAuth: true` and `forceCmkForQuery: true` (Azure's own defaults are `false`; nothing in the course uses the workspace shared keys), the Backup Vault is created with Azure Monitor alerts for all job failures enabled, and the deprecated `retentionPolicy` block is no longer sent with the storage diagnostic setting.
