# Architecture Notes: Lab 3.3 — Containers

> Learning context. These notes explain the reasoning behind the lab's design and how it would change in a real environment. The lab deliberately favors clarity over production hardening.

## 1. Design decisions & trade-offs

| Decision | Choice in this lab | Alternatives considered | Why this choice (in a learning context) |
|---|---|---|---|
| ACR SKU | Standard | Basic (~€4.20/mo, minimal storage), Premium (~€420/mo, geo-replication, private endpoints) | Standard (~€20/mo) is the "learning tier": enough storage for a few images, no complex features, not so expensive it stalls learning. Production chooses based on image volume and replication needs. |
| ACR Authentication | Admin User enabled (username/password), used by both ACI and the container app (the Portal's **Authentication type** **Secret**) | RBAC + Managed Identity (the Container App wizard's default: the environment's system-assigned identity with AcrPull), Service Principal | Admin user is simple to teach and works on all three paths with Contributor: the managed identity option makes the Portal grant AcrPull, which needs Owner or User Access Administrator, and the container instance wizard requires the admin user anyway. Production disables the admin user and uses a managed identity to avoid shared credentials. |
| Container Instances (ACI) | 1 CPU, 1 GB memory, SKU Standard, restart policy Always, public IP, TCP port 80, DNS label `<aci-name>-<suffix>` in the Unsecure (**Any reuse**) scope, no container instance logs | 0.5 CPU / 0.5 GB (lighter, slower), 2+ CPU (heavier, costlier); the Portal's default 1 CPU / 1.5 GB; the Tenant label scope the Portal switches to | 1 CPU / 1 GB is the template's size, and the guide sets it in the Portal's **Change size** pane (#228). Production right-sizes based on profiling (often smaller). Public IP teaches external access; production uses private endpoints. The Tenant scope adds a hash to the FQDN and protects against subdomain takeover, but `New-AzContainerGroup` (Az.ContainerInstance 4.x) has no scope parameter, so Unsecure is the one scope all three paths reach (#229); the guide says to keep Tenant outside the course. |
| Container Apps (ACA) | 0.25 CPU, 0.5 GB memory, 1–3 replicas, HTTP concurrency scaling, in a Workload profiles environment on the Consumption profile | Dedicated compute (App Service), serverless (Functions); a Consumption-only (v1) environment | Container Apps auto-scales on HTTP traffic; this teaches "serverless thinking" while keeping containers simple. The Portal creates only Workload profiles environments, so the template declares the Consumption profile too. Production chooses App Service for stateful apps, Functions for event-driven, or ACA for stateless microservices. |
| Image Source | ACR (private registry) | Docker Hub (public), Azure Container Registry with custom builds | Private ACR teaches proprietary image management; pulling from hub would require extra steps (az acr build). Lab assumes images are pre-built or built manually; production automates via ACR Tasks or CI/CD pipelines. |
| Container Registry Credentials | Hardcoded in Bicep (listCredentials() function) | Managed Identity with the AcrPull role on the consuming service; Key Vault reference for the admin password | This approach exposes the registry password in template outputs; production uses Managed Identity and Key Vault to avoid storing credentials in code. |
| Ingress | External (public FQDN) for both ACI and ACA | Private endpoints + API Gateway | Public ingress teaches direct container access; production places containers behind a firewall or API gateway to control traffic. |
| Monitoring | Container Apps environment logs destination **Azure Monitor** with no diagnostic setting; ACI container instance logs off. No Log Analytics workspace on any path | The Portal's defaults: a new auto-named workspace in the resource group for the environment (`workspace<rg name><suffix>`), and `DefaultWorkspace-<subscription>-EUS` in East US for ACI; Application Insights | Both Portal defaults create a workspace that costs money per GB, and the environment's one stays in `dev-skycraft-swc-rg`, where four Module 5 wizards offer it as their default workspace instead of `platform-skycraft-swc-law` (#374). Azure Monitor is the destination Microsoft now recommends and creates nothing until a diagnostic setting routes the logs. Production adds a diagnostic setting to the platform workspace for querying and alerting. |

## 2. Lab simplifications vs production

| Aspect | What the lab does | What production would require | Why it matters |
|---|---|---|---|
| Image Management | Assumes images exist or are built manually | Automated CI/CD pipeline (ACR Tasks, GitHub Actions) | Lab expects users to run `az acr build` manually; production auto-builds on git push. |
| Secrets Management | Registry credentials in template outputs | Stored in Key Vault, fetched at deploy time | Listing credentials in outputs exposes them in the deployment history. Production uses Key Vault references (identityRef). |
| Scaling | ACA: static rules (1–3 replicas, HTTP concurrency) | Dynamic scaling based on custom metrics (CPU, queue depth, custom telemetry) | Lab scaling is basic; production adds Kafka/Service Bus triggers, custom KEDA scaler rules. |
| VNet Integration | ACI: public IP only; ACA: no explicit VNet binding | Private endpoints, VNet integration, network policies | Lab containers are internet-exposed; production keeps them private and routes through API Gateway or Ingress Controller. |
| Persistence | No volumes or state storage | Persistent volumes (Azure Files, Blob), stateless design | Lab containers are ephemeral; production uses volumes for databases or caches, or redesigns to be truly stateless. |
| Security | Admin user enabled, public images | RBAC, Managed Identity, image signing, vulnerability scanning | Lab trusts all images; production scans for vulnerabilities (Trivy, Aqua) and signs images (Notary). |
| Cost Optimization | Always-on instances | Spot instances, scheduled scale-down, multi-tenancy | Lab runs 24/7; production uses auto-shutdown for non-production environments. |

## 3. Well-Architected lens (light)

- **Dominant pillar:** Operational Excellence (containers teach immutability and reproducibility)
- **Cost Management:** ACR Standard (~€20/mo, about €0.60 per day) is reasonable for learning; ACI at 1 CPU (~€35/mo on-demand) and ACA at 0.25 CPU (a few euros a month at the idle rate, much of it inside the monthly free grant) show cost differences. Auto-scale on ACA demonstrates efficient resource use.
- **Security:** ACR SKU and admin user model expose security decisions; switching to RBAC teaches least privilege.
- **Reliability:** Multiple replicas (1–3) in ACA teach redundancy without the complexity of Kubernetes.
- **Performance:** Container-native scaling on HTTP metrics (concurrency) is simpler than VM CPU-based scaling.

## 4. Cost / FinOps note

**Monthly recurring cost (if left on 24/7)**:
- ACR Standard: ~€20/mo (shared across all labs if reused)
- ACI (1 CPU, 1 GB, always-on): ~€35/mo compute (about €1.20 per day)
- ACA (0.25 CPU, 0.5 GB, 1–3 replicas, one always ready): up to ~€6/mo at the idle rate when no requests arrive, more while replicas serve traffic; the Consumption profile of the environment has no fixed charge
- **Estimated total**: about €60/mo with both ACI and ACA running, or about €2 per day. The guide's "What This Lab Leaves Behind" lists the daily costs.

**Lab cost controls**:
- Deploy ACI **or** ACA, not both, to halve the cost.
- Use spot instances (if available for containers) for further savings.
- Delete images from ACR after the lab to avoid indefinite storage charges.

**Cleanup reminder after the lab**:
- **Delete Container App Environment** (with the app; the always-ready replica is billed even when idle).
- **Delete ACI instance** (frees ~€35/mo).
- **Delete the Log Analytics workspaces** the Portal created if the environment or the container instance was created with its default logs destination; `scripts/Remove-LabResource.ps1` does (#374), but finds the container instance's one only while the instance still logs to it.
- **Delete ACR or clear all images** (frees at least storage costs; ACR registry itself is ~€20/mo).
- Images in ACR storage cost additional per GB (~€0.02/GB/mo); large images left in ACR add up.
- Orphaned Container Apps Environments with no apps still incur charges; delete these immediately.

## 5. Bicep implementation note (AVM)

- **Registry**: `avm/res/container-registry/registry` — Standard SKU with the admin user enabled (the lab's credential model) and `networkRuleSetDefaultAction: 'Allow'`, a lab-friction override (docs/bicep-standards.md §4.5): with public access enabled the module's default `Deny` adds a network rule set a Standard registry cannot accept. `azureADAuthenticationAsArmPolicyStatus: 'enabled'` is the second override: the module defaults it to `disabled`, which blocks ARM-audience tokens from the registry data plane and makes `Get-AzContainerRegistryRepository` fail with `Unauthorized`.
- **Container instance**: `avm/res/container-instance/container-group` — public IP, SKU Standard and restart policy Always spelled out, and the DNS label `<aci-name>-<uniqueString of the resource group id>`. The label scope is not set: module version 0.7.1 sends `ipAddress.autoGeneratedDomainNameLabelScope` to Azure only when `dnsConfig.nameServers` is set too (the compiled template reads `if(not(empty(tryGet(parameters('dnsConfig'), 'nameServers'))), ..., null())`), and this template has no `dnsConfig`, so the value would be dropped. Azure then applies its default, Unsecure, the scope the Portal steps choose and the one `New-AzContainerGroup` (which has no scope parameter) leaves; the first live Bicep deployment confirms it in `IpAddress.AutoGeneratedDomainNameLabelScope`. The FQDN is composed in an output because this module version returns only the IPv4 address, and the composition holds only for that scope.
- **Container Apps environment**: `avm/res/app/managed-environment` with the §4.5 overrides `zoneRedundant: false` (the default needs an infrastructure subnet) and `publicNetworkAccess: 'Enabled'`, the Consumption workload profile the Portal adds (`workloadProfiles`), and `appLogsConfiguration.destination: 'azure-monitor'`, which creates no Log Analytics workspace. The module also sends an infrastructure resource group name (its default, `take('ME_<name>', 63)`), but an environment without an infrastructure subnet gets no such group: on 2026-10-26 neither the Bicep nor the Portal path left an `ME_` group, and `infrastructureResourceGroup` stayed empty (#433 decides whether the `-02` suffix stays). A Workload profiles environment cannot be turned into a Consumption-only one or back, so an environment deployed by an older version of this template (without `workloadProfiles`) has to be deleted before this one is deployed (Azure no longer creates Consumption-only environments: on 2026-10-26 two requests without workload profiles both got the Consumption profile, so only an older environment can be one): `Deploy-Bicep.ps1` looks for one before it changes anything and stops, naming `Remove-LabResource.ps1`.
- **Container app**: `avm/res/app/container-app` — `workloadProfileName: 'Consumption'`, external ingress with `ingressAllowInsecure: false` and 1–3 replicas scaled on HTTP concurrency; the module also sends `maxInactiveRevisions: 0`. It pulls with the registry's admin credentials and has no managed identity, as the Portal's **Secret** authentication type leaves it.
- **Cleanup** (`scripts/Remove-LabResource.ps1`): the app, the environment, then the Log Analytics workspaces that exist only because of this lab (#374; no other lab uses them, Module 5 uses `<env>-skycraft-swc-law`): the one the environment logs to, found by relation (the customer id in its `appLogsConfiguration`) anywhere in the subscription and whatever its name, and any in the resource group that carries the Portal's automatic name; then the container instance and the registry. Last, the workspace the container instance logged to (the ACI wizard's default), found through the instance's diagnostics customer id, is deleted when it is Azure's default `DefaultWorkspace-<subscription id>-<region>` in `DefaultResourceGroup-<region>`, and that group with it when nothing else is in it; a group that still holds something is kept and its contents named, and a workspace with another name is named and kept. A workspace named `<anything>-skycraft-swc-law` (Lab 5.1's shared workspace) is never deleted, whatever points at it: the script names it with a `[WARN]`. A workspace stays while the environment or instance that logs to it could not be deleted, and a lookup that fails is a counted failure, never read as absent. Every delete is confirmed, and shown under `-WhatIf`, by the name of the resource it targets. `scripts/Test-Lab.ps1` fails on an auto-named workspace, on container instance logs and on an environment that sends its logs to Log Analytics.
- **Two-phase deployment**: `bicep/acr.bicep` is the bootstrap entry point for phase 1, so the image can be imported into the registry before `main.bicep` deploys ACI and the container app. `Deploy-Containers.ps1` is retired — `Deploy-Bicep.ps1` performs the same steps.
- **Names follow the environment** (#121): every resource name defaults to a `parEnvironment` / `-Environment` prefix — `<env>-skycraft-swc-rg`, `<env>skycraftswcacr01`, `<env>-skycraft-swc-aci-auth`, `<env>-skycraft-swc-cae-02`, `<env>-skycraft-swc-aca-world` — in the templates and in all three scripts, so `-Environment prod` deploys, validates and tears down prod resources. The names stay parameters (`-AcrName`, `-AciName`, `-CaeName`, `-AcaName`) because the registry name is global and because a resource deployed under an older scheme can only be removed by naming it. The app has no `-02`: nothing immutable hangs off its name and the platform variant would exceed the 32-character Container App limit.
